First, the idea

You know the drift story — a component exists twice, once as the design you decided and once as the code that ships, and the two never quite stay the same. A contract is the way out: a third, small file that both copies answer to.

Design intent
what you decided — options, tokens, behavior
⇄
The contract

button.contract.json
⇄
Shipped code
what actually renders, in the repo
THE CHECKERcompares the contract to the code and names the exact place they stopped agreeing — a check you run, not an opinion you form.

The file is a form with boxes, not a paragraph. A paragraph has to be understood, and understanding varies; a form only has to match, and matching gives the same answer every time. That is the whole trick — in Nathan Curtis's words, a description informs; a contract arbitrates. Six boxes carry it:

name + description
What this is, and when to reach for it. The sentence a partner reads before choosing it.
system
Which design system governs it — this repo has four, and the wrong answer here makes every other box wrong.
props
What you may vary, and the exact options for each. The fence: anything on the list is yours to use freely.
tokens
The named decisions it reads for color, radius, spacing — never a raw value. Change the token, and everything built on it moves together.
gaps
What it cannot do yet, and why. The gate: a refusal you wrote in advance, so nobody has to improvise a no.
bindings
Where the real code lives, so the checker can find it and hold both sides to the same story.

What makes a contract great is not a matter of taste. Nathan Curtis — the system architect who coined components-as-data — names seven facets, and this skill adopts them as its principles. Every check and every recommendation below traces to one:

NC-1

Well-typed over loosely formed

Every value has a legal shape — one choice from a fixed list, a yes/no, a number. A contract that accepts any text cannot reject size: kind of large.

NC-2

Normalized over redundant

Each decision is stated once. The moment it lives in two places the contract can disagree with itself, and a self-contradicting artifact cannot arbitrate anything.

NC-3

Independent over platform-biased

No party owns it — not Figma, not React. A definition biased to one party's point of view is testimony, not a contract. Platform detail lives at the edge, in the bindings.

NC-4

Verifiable over readable

A machine can rule it right or wrong — validly formed, and precisely implemented. Reading is review, not verification.

NC-5

Deterministic over inferred

Same input, same output, empty diff. Deterministic compilation isn't the goal — it's evidence the contract is good.

NC-6

Efficient to keep true

The cost that matters is keeping it current, not writing it. A rotted contract is worse than no contract at all, because people trust contracts.

NC-7

Evolvable over simply flexible

Strict does not mean static. A contract that can't change dies, and a contract that changes without governance was never actually a contract. Growth happens through reviewed proposals, and the schema is versioned separately from every contract written against it.

The one rule

The copies never update each other directly. A change — a new option, a different color — goes into the contract first, gets reviewed there, and both sides follow. One source in the middle, and nobody crowned.

Walk one component through it

A button — the component everyone thinks is too simple to need a contract, which is why it is the right one to show. Everything below is your real components/ui/button.tsx, and the finding had been shipping for months.

The component, before anything

A shadcn Button styled with cva. Seven variants, ten sizes — seventy combinations, all correct, in one 74-line file that two people had reviewed. Nobody had complained about it.

The contract

Written from that file, not from what anyone wished it said. Under 60 lines, and every line is checkable.

"props": [

Every <Button>Save</Button> in the app renders 32px tall, not 36. The stated default has never once applied.

And nothing looks broken. Both values make a real button. It passes every test, renders in both themes, and reads as correct to anyone opening the file — because the wrong line is the one that looks most authoritative. A linter has no opinion, a type-checker is satisfied, and a review sees two sensible defaults with no reason to compare them.

A contract catches it because a contract can only hold one answer. Asking “what is the default?” out loud is what turns two answers into a failure instead of a coincidence. NC-2

The card that falls out

Findings

Three specialists read the same work. The lens tells you who is speaking; the recommendation is theirs. Where something went wrong, it is a gap in the tool, not a mistake by whoever wrote the component.

#LensReads asFindingRecommendation
EN-1ENGINEERCRITICAL The rival-rule check cried wolf 23 times.It counted the button's own hover state as a rival, and it suspected rules like .beat p that can never touch a link. NC-4 Let each part say what element it renders, so rules that could never reach it are dismissed on sight. Treat a part's own hover and focus as the same owner in another state. The two real catches survive both fixes.

The card a partner reads before prototyping — the reason you asked for this skill — is still a stub. Write that card next. Its test is concrete: someone given only the card can build a flow that passes the checker without one hardcoded value.
EN-2ENGINEERSTRENGTH The real catches are real.Your Button declares its default size in two places that disagree, and the sketchbook CTA loses its own text color to a page-wide rule. Both found on the first run; neither known before. NC-4 · NC-5 Keep the fail-loud stance: when the checker cannot read a file it says so and fails, instead of passing in silence. Write today's five sabotages into MUTATIONS.md as the permanent record.
PD-2PRODUCTSTRENGTH Writing a contract found a missing component.The sketchbook CTA turned out to be two loose classes inside a 500-line page — which is exactly why its bug could ship. The checker's confusion was pointing at the real problem. Make this a designed outcome: when extraction cannot find a component, the skill says “this wants to be a component” and shows the boundary it was looking for.
VD-1VISUALSTRENGTH The contract can explain a no.Its gaps field holds refusals you wrote in advance: “no success variant — a third signal color is a token decision, not a component decision.” A partner hears the system's reasoning, in your words. NC-7 Carry gaps word-for-word into every partner card, so a refusal always arrives in the system's voice rather than an agent's improvisation.
VD-2VISUALGAP A contract has no picture.The file names every option, but a designer cannot see a contract — and your component gallery, which shows exactly this, is never mentioned. Give the contract an optional link to its gallery entry, and put that link on the partner card beside the option list.
VD-3VISUALGAP The list of allowed states is closed.Six states are built in. A groovebox key is armed or playing, and the schema has no way to say so — the same rigidity Vallaure's article complains about in Figma variants. NC-1 · NC-7 Accept any state name, keep the six as documented conventions, and have the checker mark unknown states as unverified rather than invalid.
VD-4VISUALGAP For Tailwind components, the styling section covers less than it appears to.Utility classes carry most of the real styling; the contract governs the token references it can see. A designer reading it would assume it is the whole picture. NC-2 Curtis settles this one: state each decision once, and delete what cannot be verified. Govern the option axes, defaults, semantics, and the token references the checker can map — and remove the styling claims it cannot. If deleting a sentence changes nothing checkable, it was never part of the contract.
EN-3ENGINEERGAP The hardcoded-color scan reads the whole stylesheet.It flagged a color in a gradient that has nothing to do with the button. Right instinct on a small component file; a flood on a page-sized one. NC-4 Scan only the rules that style the contracted parts, including their states.
EN-4ENGINEERGAP The color net has holes.The scan recognizes hex values only — rgb() and oklch() walk past it, and a Tailwind value like bg-[#b8559b] is never looked at. NC-4 Widen the net to every color notation, add a scan of class strings on the Tailwind side, then sabotage both spellings — the house rule for any guard.
EN-5ENGINEERGAP Misspell a field and every check quietly passes.The schema forbids unknown fields, but the checker never enforces that. A typo in props would switch off most of the checking without a word — and a format where nothing is invalid is a format where nothing is verifiable. NC-4 Walk the contract for unknown keys before checking anything. Ten lines, no dependency, and it closes the quietest failure in the file.
PD-3PRODUCTGAP The version number does not mean anything yet.Change requests have a file format, but nothing says what accepting one does — nothing bumps the version, so the version carries no information. NC-7 Define it: minor bump for a new option or prop, patch for a fix. Accepting a change means: apply it, bump the version, change the code, re-run the checker — in that order. A change that reshapes the contract itself also gets a short decision record beside it, so the shape has a history.
PD-5PRODUCTGAP The schema and the contracts shared one version.The model of what a contract can say, and each contract's own content, move on different clocks — implementing depends on both. NC-7 Fixed during this review: the schema now carries its own version and its address names it (/v1/). Each contract records which schema it was written against.
PD-4PRODUCTGAP 128 components, no rule for which deserve contracts.A contract nobody prototypes against is inventory with a maintenance bill attached. NC-6 Contract the prototyping kit only — the five to eight components partners actually reach for. Write that scope into the skill itself so extraction stays narrow on purpose.
EN-6ENGINEERGAP The checker reads code by pattern, not with a real parser.An arrow-function component or a variant table held in a variable would defeat it. Acceptable only because it fails loud when it cannot read. NC-5 Every code shape the checker claims to read gets its own sabotage test before the skill ships. A shape nobody watched fail is a shape that is not supported.

Two findings worth slowing down for

ENGINEER  EN-1 · Why the 23 false alarms matter more than the 2 bugs

The two real catches make the skill look finished. They are the trap. Your own working rule says a guard that fires on correct code is as broken as one that never fires — it teaches the person reading it to stop reading. Twenty-three findings deep, the one real catch is background noise.

Here is that real catch on its own. Specificity is the score CSS uses to pick a winner when two rules want the same property — and the contract's rule loses:

.btnPrimary
0,1,0
the contract's rule · color: var(--ground)
.page a
0,1,1
the winner · color: inherit → ink on ink

The value you decided is written, matched, and loses — the source reads correct while the button renders wrong. No linter sees this class of bug, which is why this check earns its place. The fix is aim, not ambition: once a part says it renders a link, rules on em, p and h3 are dismissed on sight, and the part's own hover is recognized as the same owner in another state.

PRODUCT  PD-2 · The checker's most confused finding was its most useful

“The contract says a, the code renders div” sounds like the checker failing — it had read the root of a 500-line page, because that page is where the CTA lives. But its confusion points at the real problem: the sketchbook CTA is not a component. It is two loose classes in a page stylesheet, which is exactly how a black-on-black button shipped without any test noticing. Where extraction cannot find a component, that is a map of what should become one next. The skill should say this on purpose instead of stumbling into it.

What good looks like

Three artifacts a user of this skill should expect to produce, drafted from today's real Button contract. This is the standard the skill is aiming at.

A contract that can refuse

BEST CASE
"props": [{
  "name": "variant",
  "type": { "enum": ["default","outline","secondary","surface","ghost","destructive","link"] },
  "default": "default"
}],
"gaps": [{
  "what": "No success or warning variant.",
  "why":  "The palette carries one accent and one destructive; a third
           signal color is a token decision, not a component decision."
}]

Why it works: the option list is the fence and the gap is the gate. When a partner asks for the thing outside the fence, the answer already exists, in the system's own reasoning — nobody improvises a no, and nobody invents a green button at 4:50 on a Friday.

The card a partner actually receives

BEST CASE
## Button — what you may use
variant   default · outline · secondary · surface · ghost · destructive · link
size      default · xs · sm · lg · xl · xxl · icon · icon-xs · icon-sm · icon-lg
see it    /component-gallery#button

Color, radius, spacing: only through tokens this component already reads.
Never restyle it, never fork it, never write a hex value.

## If your flow needs something not on this card
Do not invent it. Say “the system can't do this yet” and file the ask:
  { "prop": "variant", "add": "success", "because": "…" }

Why it works: this is the 69-versus-100 result from Southleft's test, turned into a working rule. An agent left to taste scored 69 out of 100 — it invented options and hardcoded colors. The same agent handed a strict rulebook scored 100, because it was allowed to say no. The refusal rule is the card; the tables are what makes the rule fair.

The honest refusal, end to end

BEST CASE
Partner, prototyping a checkout flow“Make the confirm button green so it reads as success.”
Agent, holding the contract“The system can't do this yet — Button has no success variant, and the contract says why: a third signal color is a token decision. I built it with default and filed a request for variant: success. If it's accepted, this screen picks it up with a one-word change.”
Librarian, in reviewAccepts the request → adds the token pair → widens the option list → bumps 1.0.0 → 1.1.0 → code follows → checker green.

Why it works: the system grew by one honest step, and it grew in the contract first. The prototype never lied about what the system could do, and the review happened where a review can happen — on a one-line change to a small file, not on a rendered screen someone already loves.

Back to step 3, forever

The loop has no end state. What it has is a cost near zero per turn — one command, seconds, an exit code — which is the only reason a contract stays true instead of rotting while everyone still trusts it. NC-6

What made this correct: the system was named first, the contract was written from real code, the first run was allowed to fail, the fix went into the contract before the code, the partner read a generated card rather than the file, and the one thing the system could not do was refused out loud and then built properly. Six moves, one component, and not one of them needed a design tool.
